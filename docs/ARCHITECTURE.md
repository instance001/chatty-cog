# ChattyCog Architecture Notes

Design stance:

- local-first is the baseline
- cloud is optional and user-supplied
- hybrid workflows are first-class
- model choice belongs to the operator, not the tool

In practice, ChattyCog now treats "model selection" as a shared routing problem rather than a local-GGUF-only assumption. The orchestrator and Bookkeeper can each target either a local GGUF lane or a BYO cloud lane, with provider adapters deciding what each lane can actually do.

## Components

### GUI (Rust, eframe/egui)

- `src/main.rs`
  - Tabbed UI shell (Chat / Models / Logs / Networking / Sandbox / Settings / About + Modules)
  - Orchestrator chat loop with streaming tokens
  - Runtime status badge in Chat so the user can see whether the active lane is local GPU/Vulkan, local CPU, cloud, or error path
  - Unified chat-header model selector with live model switching across local GGUF and BYO cloud entries, plus quick-open, refresh, voice status, and live chat token readout
  - Collapsible assistant reasoning view in each assistant bubble plus inline interrupt control in the chat composer
  - Wait-state guard in the composer so extra user turns cannot be injected while inference is already running
  - Three-column chat layout with anchored Hot Memory / active context and Luke Warm / rolling summary side panels around the transcript
  - Transcript and assistant thinking views are width-clamped to the center panel to prevent long-session horizontal creep
  - Heuristic cleanup for leaked / repeated reasoning so obvious draft loops get siphoned out of visible replies and duplicate streamed suffixes are trimmed
  - Capsule library product surface for reusable behaviour/style profiles, stored in preferences and optionally layered into the orchestrator system prompt
  - Hot Memory panel for active context (user-visible recent/pinned items)
  - Logs UI (semantic search + keyword search + log folder explorer)
  - Sandbox explorer/editor (`Chatty_Sandbox/`)
  - Orchestrator sandbox tool requests (user-approved write/append/read/list/preload/ledger within `Chatty_Sandbox/`)
  - Explicit composer-level sandbox task mode (`Create file` / `Edit file` + target path) that wraps the current user turn in deterministic sandbox instructions before generation
  - Persistent sandbox scratchpad (`Chatty_Sandbox/scratchpad/current.md`) injected back into the prompt as durable working notes
  - Structured task ledger (`Chatty_Sandbox/scratchpad/task_ledger.md`) injected back into the prompt for current task / next step / open questions / files touched
  - Multi-step prompt detection that nudges the orchestrator toward sandbox preload + ledger use when a task looks long or structured
  - Dynamic module discovery + tabs (`modules/*/manifest.json`)
  - Module workspace surfaces:
    - `ui.json` form -> `state.json`
    - fallback editor -> `workspace.md` (seeded from `STATE_TEMPLATE.md` when present)
  - Module on-suspend debrief (manual or auto-generated by Bookkeeper)
  - Optional per-module AI runner (demo) when a manifest sets `ai_enabled: true`
  - Preferences system (`config/preferences.json`) for orchestrator/bookkeeper defaults, optional cloud model registry, and per-module defaults

### Host-owned capability orchestration

- `src/capability_orchestrator.rs`
  - host-owned normalization layer over module-declared capabilities
  - converts manifest/network capability declarations into authoritative host records
  - groups declared publish/receive lanes into a reusable registry instead of scattering feature checks across UI and networking code
  - gives ChattyCog a stable place to answer questions like:
    - which modules are room-capable
    - which modules are host-authoritative
    - which hosted asset lanes can accept a given incoming artifact
  - intended future insertion point for execution policy, capability gating, and host-led routing decisions

### Cloud / hybrid routing

- `src/cloud_ai/mod.rs`
  - resolves saved cloud entries into lane-aware targets
  - exposes provider capabilities so selectors can hide entries that do not satisfy the current lane
  - builds the right provider adapter only when the user explicitly selects a saved cloud entry
- `src/cloud_ai/openai_compatible.rs`
  - OpenAI and generic OpenAI-compatible chat + embeddings adapter
- `src/cloud_ai/anthropic.rs`
  - Anthropic chat adapter for the orchestrator lane
  - current adapter does not expose embeddings, so Anthropic entries are filtered out of the Bookkeeper lane
- `src/cloud_ai/gemini.rs`
  - Gemini chat + embeddings adapter via Google's current OpenAI-compatible endpoint family
- local use does not require any cloud lane

### llama.cpp runtime integration (Option B)

- `src/llama_dyn.rs`
  - Loads `runtime/windows/llama.dll` and `runtime/windows/ggml.dll` dynamically
  - Loads ggml backends from a folder (`ggml_backend_load_all_from_path`)
  - Initializes llama / ggml backend loading once per process so repeated turns do not keep registering backends until the scheduler assert trips
  - Tracks live runtime handles so backend state is reset safely when the last runtime instance drops
  - Runs:
    - GPU-allowed chat generation (`generate_chat`)
    - CPU-only generation (`generate_text_cpu_only`)
    - CPU-only embeddings (`embed_text_cpu_only`)

### Memory / Bookkeeper Support Role

- `src/memory/bookkeeper.rs`
  - Runs in its own thread
  - Records audit-history events to `memory/cold_log.jsonl`
  - can run on either:
    - local llama.cpp lane
    - BYO cloud lane with chat + embeddings endpoints
  - Provides:
    - semantic search (cosine similarity, brute-force over stored vectors)
    - optional filters by `module_id` and/or `tag`
    - keyword fallback handled in GUI
    - `Luke Warm` rolling summary stored in `memory/lukewarm.txt`
    - module status updates stored in compatibility files:
      - `memory/departments.md` (human / orchestrator injection)
      - `memory/departments.json` (machine-readable)
- `src/memory/governor.rs`
  - host-owned cold-memory retrieval layer beside the existing Bookkeeper logs
  - current first slice powers the user-triggered Remember path
  - reads `memory/cold_log.jsonl` as exact historical evidence without rewriting it
  - limits v1 retrieval to pure user/assistant interaction events
  - extracts the matched exchange plus one complete exchange before and after where available
  - preserves source path, event indexes, timestamp metadata, and the exact bounded transcript block
  - surfaces recall lane, bucket, placement, and reason metadata in Remember result cards before attachment
  - renders selected cold context under a host-owned boundary that says it is historical evidence, not current truth
  - exposes the host-owned Remember injection renderer used by Main AI system prompt construction
  - appends compact Remember recall-session receipts to `memory/remember_recalls.jsonl` for searched/cancelled/attached outcomes, linked by a timestamp-plus-sequence `recall_id`
  - appends compact Remember attachment audit receipts to `memory/remember_attachments.jsonl` linked by `recall_id` without storing hydrated transcript text
  - appends compact Remember feedback receipts to `memory/remember_feedback.jsonl` when the user marks a proposed result stale, misleading, or noisy
  - annotates future Remember candidates with prior feedback counts for the same bounded evidence without suppressing or mutating the result
  - includes Remember recall/attachment receipts grouped by `recall_id` in the Logs tab governance receipt viewer
  - filters the rendered governance receipt view without changing receipt files
  - exposes a Logs-tab recall route preview that summarizes atlas, semantic, direct cold-log lanes, and post-merge Remember candidate order without attaching context or writing recall receipts
  - does not promote selected material into active context, rolling summary, module status updates, or durable memory
- `src/memory/cold_atlas.rs`
  - first inspectable data model for broad cold-memory shape records
  - stores atlas records in `memory/cold_atlas/atlas_records.jsonl`
  - stores atlas governance receipts in `memory/cold_atlas/atlas_receipts.jsonl`
  - requires each atlas record to point down to at least one `ColdEvidenceRef`
  - records status/currentness and confidence without claiming present-day truth
  - exposes read-only atlas and receipt renderers for the Logs tab
  - prepares atlas draft prompts from approved semantic placements without hydrating transcript payloads
  - can ask the existing Bookkeeper lane to draft cold-atlas JSON into an editable UI field
  - validates pasted atlas JSON against the prepared evidence IDs before preview or commit
  - requires the exact current JSON to be previewed before atlas records can be committed
  - lets the user mark atlas records as `needs_review`, `stale`, `retired`, or restored to `historical_shape` from the Logs tab
  - rewrites only atlas record status/update metadata for status changes, then appends compact transition receipts without transcript payloads
  - lets the user inspect each atlas evidence ref by hydrating the exact bounded cold-log context through the governor without revising, injecting, promoting, or rewriting memory
  - lets the user stage an existing atlas record for revision, prefilled as editable JSON from its current evidence refs
  - requires revision preview to show before/after state before committing a same-id in-place revision with a compact `revised` receipt
  - lets the user stage a supersede flow that creates a new replacement atlas record, marks the old record `superseded`, and links both compact receipts by related atlas id
  - renders read-only atlas lineage rows from linked receipts so superseded records remain inspectable without being normal Remember candidates
  - lineage rows expose old/replacement evidence inspection buttons that hydrate exact cold-log context without recalling it into Main AI
  - exposes a Logs-tab atlas query preview that runs the same atlas recall policy without hydrating evidence, injecting context, or promoting memory
  - provides a deterministic atlas query lane for Remember over atlas title, summary, scope, note, and tags
  - excludes `retired` and default-excludes `superseded` atlas records from normal Remember recall; superseded records are available only through explicit lineage-style query
  - atlas Remember hits are hydrated through the governor into exact bounded cold-log transcript candidates before user selection
  - keeps atlas explanation metadata visible in Remember cards while excluding atlas summaries from the exact payload that can be attached
  - is not wired to automatic summarization, promotion, or direct Main AI injection
- `src/memory/semantic_index.rs`
  - inspectable data model for the meaning-sorted cold retrieval lane
  - defines semantic buckets, evidence refs, bucket placements, sift proposals, and sift receipts
  - mirrors the semantic-sorter shape: positive buckets plus exactly one required misc bucket for weak or non-fitting evidence
  - provides the starter v1 interaction bucket map used by the Logs tab bootstrap control
  - stores references and metadata over cold evidence rather than replacement transcript text
  - keeps bucket placement and bucket sifting reviewable before mutation by requiring user-selected approval/apply receipts
  - can use prior Remember noise/misleading feedback as a review signal during bucket-sift proposal generation
  - marks selected feedback-driven sift changes as `needs_review` instead of silently rejecting evidence
  - applies approved sift changes only to the semantic placement index; cold logs remain the immutable evidence source
- `src/memory/semantic_sorter.rs`
  - prepares bounded cold-log interaction evidence after the latest semantic sort cursor
  - renders an inspectable sorter prompt against the frozen bucket map
  - parses pasted sorter JSON and commits only validated proposed placements plus a receipt
  - can ask the existing Bookkeeper lane to draft sorter JSON, leaving the result in an editable UI field
  - renders a review preview from the same parser used by commit, so invalid bucket decisions are caught before writing
  - requires the exact current JSON to have a successful preview receipt before commit is enabled
  - exposes a read-only bucket placement overview so proposed refs are inspectable without copying transcript text into the index
  - keeps sorter-created placements in `proposed` status until the user approves or rejects them from the Logs tab
  - shows bucket labels/descriptions, review status, and bucket/fit filters during placement review
  - includes `needs_review` placements in the same explicit approve/reject review queue
  - lets proposed placement review hydrate exact bounded cold-log context for inspection without approving or injecting it
  - appends durable placement-review receipts with status transitions when user approval/rejection is applied
  - exposes sort, placement-review, and sift receipts in a read-only governance receipt viewer
  - supports a Logs tab bucket-sifting panel that proposes duplicate/weak-fit cleanup, lets the user inspect exact evidence, and applies only selected changes
  - uses approved placements only for semantic Remember lookup
  - exposes a Logs-tab semantic bucket query preview over approved placements without hydrating evidence, injecting context, or promoting memory
  - has an end-to-end memory test covering proposed placement inertia, user approval, semantic recall, bounded hydration, and selected attachment rendering
  - remains host-bounded: no automatic sorting, no transcript rewriting, and no promotion into current context

## Cold log envelope (schemaless)

Module events are treated as schemaless envelopes with a few universal index fields plus an optional free-form payload.

Required intent fields (current usage):
- `ts` (unix ms)
- `cat` (`chat` | `module`)
- `source` (e.g. `user`, `assistant`, `ui`, `module`)
- `module_id` (module name; historically described as department, empty for pure chat)
- `event_type`
- `summary` (short human text)

Optional:
- `tags`: string array (user-assignable)
- `entities`: string array (reserved for later)
- `payload_json`: string (free-form JSON text)

Note: the JSONL writer currently includes some duplicate keys for backwards-compat (`module`/`module_id`, `type`/`event_type`, `text`/`summary`). The parser prefers the new keys.

## Memory tiers (intended)

- Active context (`Hot Memory` UI label): small, user-visible list of pinned/recent items.
- Module status updates (`departments.*` compatibility files): latest per-module debriefs for cross-module context.
- Rolling summary (`Luke Warm` UI label): summary to keep context usable without bloating prompts.
- Audit history / event log (`cold_log.jsonl`): full append-only record for later retrieval.
- Remember (host/governor): deliberate user-triggered recall from cold logs. Search proposes bounded historical candidates; the user selects; the host injects only selected exact transcript blocks into the next Main AI turn.
- Cold semantic index: meaning-sorted buckets over exact evidence refs. Approved placements reduce retrieval cost, then hydrate exact surrounding context from the linear cold log before user selection.

Working doctrine:

```text
Active context keeps selected details close.
Rolling summary orients the current thread.
Cold semantic index remembers the shape.
Audit history remembers the specifics.
Remember is deliberate recall, not automatic belief.
```

## Orchestrator system prompt injection

Before each generation, the Chat tab reads:
- `memory/departments.md` (compatibility filename for latest per-module "what happened" updates)
- `memory/lukewarm.txt` (rolling summary / recent activity rollup)
- optional user-selected Remember attachments for the next send only

and injects them into the orchestrator system prompt.

If the user has activated a behaviour profile from the Capsule library product surface, that profile is also layered into the orchestrator system prompt as an explicit style/behaviour overlay.

Remember attachments are injected under `USER-SELECTED COLD LOG CONTEXT`. They are cleared immediately after prompt construction so cold-log evidence does not remain silently active across turns.

## Known fragile surfaces

These are the UI paths most likely to regress during layout or state refactors.

### Chat layout contract

- The Chat tab assumes a three-column layout: `Hot Memory`, transcript, and `Luke Warm`.
- Long transcript content must wrap inside the center column instead of renegotiating the overall workspace width.
- Read-only assistant "thinking" content is especially sensitive because non-wrapping editors can silently force horizontal creep if they are embedded in the transcript.

### Composer focus contract

- The chat composer should survive ordinary layout churn while the user is typing.
- Dynamic helper rows above the composer, such as sandbox hints or approval blocks, can change the vertical layout from one frame to the next.
- If those rows appear or disappear while the composer is active, focus recovery logic needs to keep the text input usable without requiring a reclick.

### Luke Warm refresh contract

- `lukewarm_summary` is displayed in both the Chat tab and Logs sidebar, but it is refreshed by a time-based poll loop in the main app update path.
- That poll loop depends on scheduled repaints as well as the background receiver state.
- If repaint scheduling is removed or weakened, Luke Warm can appear to "freeze" even though the underlying summary source is still changing.

### Regression guardrail

- Use [CHAT_UI_SMOKE_CHECKLIST.md](CHAT_UI_SMOKE_CHECKLIST.md) after changes to chat layout, composer behavior, Luke Warm rendering, or sandbox approval surfaces.
- Treat width drift, focus loss after a short pause, and idle Luke Warm polling stalls as first-class regressions, not cosmetic issues.

## Packaging direction

The app resolves one active base path and creates the standard working folders on first run. During development that base is the source checkout root. In a packaged unzip-and-run release it is the folder beside `chattycog_gui.exe`. `CHATTYCOG_BASE_PATH` can override the base for portable/shared deployments.

The repo layout keeps `models/`, `runtime/`, `memory/`, `modules/`, and `Chatty_Sandbox/` at the active base so a packaged app can still ship a single directory tree:

```
chatty-cog/
  chattycog_gui.exe
  runtime/windows/*.dll
  models/*.gguf
  modules/*
  memory/*
  Chatty_Sandbox/*
```

First-run startup creates the empty working folders when they are missing. Keep model files and runtime DLLs out of git and place them into the packaged release folder or a `CHATTYCOG_BASE_PATH` location.
